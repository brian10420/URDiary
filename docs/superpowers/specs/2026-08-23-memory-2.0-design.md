## §0 一句話

把「每次整份重寫、無強制上限」的互動筆記，升級成 Hermes 式的兩份硬上限常駐檔（使用者檔案＋陪伴者筆記）——對話後 review pass 以 add/replace/remove 結構化 ops 增量寫入、逐筆帳本可撤銷可核可、使用者全文可編輯，檢索軌從 LIKE 升級 FTS5。

## §1 範圍、非目標與裁決記錄

**做**：
1. 兩份 per-user 常駐記憶檔（`memory_files` 表）：使用者檔案 800 字＋陪伴者筆記 600 字，硬上限強制、80% 軟門檻提示整併。
2. 對話後 review pass 取代現行互動筆記整份重寫：單次 LLM 呼叫輸出 JSON ops（add/replace/remove），純 Python 引擎驗證套用；超標 retry-with-feedback 一次，仍超標整批拒絕。
3. 治理：`memory_write_mode` 可切換（預設自動制），核可制下 ops 進 pending；逐筆帳本（`memory_ops` 表）恆在，applied 可撤銷。
4. 設定頁「記憶」區＋獨立記憶管理 modal（三 tab：兩檔全文編輯＋帳本）；核可制下日記完成後聊天區溫暖通知。
5. 懶遷移：首次 review pass 以舊互動筆記為素材自然 seed；seed 前注入 fallback 舊筆記，零手動步驟。
6. 關鍵字檢索軌 LIKE→FTS5＋bm25（jieba 斷詞入索引；day_notes 小語併入索引），LIKE 保留為降級路徑。
7. Spec B／D／E 三邊接縫（見 §3）。

**非目標（本期不做）**：
- 不做 agentic tool-loop（多輪 tool-calling 寫記憶）——`llm.py` 須為五家供應商各實作工具協定，破壞「單次 completion 相容所有供應商」底盤。Hermes 的「工具在對話迴圈內」適配為「寫入全在對話後 review pass」。
- 不做日記搜尋框 UI（索引屆時現成，留給 Spec D 日記頁改版順勢加）。
- 不做聊天歷史入 FTS 索引（須改 200 則/30 天修剪為永久保留；日記本就是對話的策展產物，重複性高）。
- 不做「背景任務用便宜模型」的設定 UI（Spec E 模型層的事；本期 review pass 沿用 session cfg）。
- 不做字數上限的使用者設定 UI（常數集中一處，先用推薦值測試一段時間再議調升）。
- review pass 不再巢狀呼叫 `analyze_emotion_trends`（省每次日記一整次 LLM 往返；素材價值由 day_notes 近 14 天軌跡＋當日 valence 取代）。`analytics_service` 本體與其 API 不動。
- 不刪 `interaction_notes` 表與資料（停寫保留、歷史唯讀）。

## §2 資料模型與雙檔結構

### memory_files（兩份常駐檔，存 DB）

| 欄位 | 型別 | 說明 |
|---|---|---|
| id | Integer PK | |
| user_id | FK users.id, index | |
| file_key | String(16) | `user_profile` / `companion_notes`；Unique(user_id, file_key) |
| content | Text | 檔案全文（含 `## ` 章節標題） |
| updated_at | DateTime | |

檔案列**懶建立**：首次寫入（review pass seed 或使用者編輯）才產生；不存在＝還沒開始記。

**`user_profile` 使用者檔案（800 字）——他是誰**。章節骨架（v1 分區結構＋現行 v2 精華融合）：

```
## 稱呼與身分
## 四大生活領域        （家庭／學業工作／人際／自我發展，每條末尾 (YYYY-MM-DD)）
## 情緒模式            （主要情緒主題、觸發因素、有效的調節方式）
## 重要事件時間線      （- [YYYY-MM-DD] 事件一行摘要，含情緒影響與應對；最新在前）
## 優勢與關鍵洞察
```

**`companion_notes` 陪伴者筆記（600 字）——怎麼陪他**（Hermes MEMORY.md 等價物，陪伴者寫給自己的工作筆記，不向使用者複誦但照著做）：

```
## 有效的支持方式      （「他累的時候不喜歡被追問」「聊研究時要當思考夥伴」）
## 進行中的關注        （「下週二面試，之後可以問問結果」）
## 觀察與提醒          （自由觀察區）
```

日期慣例全沿用 v1：每條資訊末尾 `(YYYY-MM-DD)`、時間線條目 `[YYYY-MM-DD]` 前綴。

### memory_ops（逐筆帳本＝pending 佇列＝稽核軌跡）

| 欄位 | 型別 | 說明 |
|---|---|---|
| id | Integer PK | |
| user_id | FK users.id, index | |
| file_key | String(16) | 目標檔 |
| batch_id | String(36) | 一次 review pass／一次使用者編輯＝一批（uuid） |
| action | String(12) | `add` / `replace` / `remove` / `user_edit` |
| section | String(40) nullable | add 的目標章節（白名單）；replace/remove 為提示用途可空 |
| target_text | Text nullable | replace/remove 的精確目標原文（substring 比對） |
| new_text | Text nullable | add/replace 的新文字；user_edit 存編輯後全文 |
| status | String(12) | `applied` / `pending` / `rejected` / `undone` / `stale` / `failed` |
| source | String(20) | `review_pass` / `diary_ingest` / `onboarding` / `user_edit` / `migration` |
| source_diary_id | Integer FK diaries.id, nullable | 這筆記憶來自哪篇日記（可追溯；刪日記時服務層置 NULL，同 day_notes 慣例） |
| error | Text nullable | failed/stale 的原因（如「找不到原文」「超標整批拒絕」） |
| created_at / decided_at | DateTime | decided_at＝核可/拒絕/撤銷時間 |

狀態語意：
- **applied**：已生效（自動制直接套用；核可制核可後套用）。可撤銷→undone。
- **pending**：核可制下等待使用者決定。核可時以**當下**檔案重驗 target，比不到→stale。
- **failed**：套用時 target 比不到或整批超標未套用——帳本可見，不擋其他筆。
- **stale**：使用者編輯檔案或先套用的 op 使目標原文消失，該 pending 失效。
- **undone**：使用者從帳本撤銷（反向 op：add→移除該句、remove→補回、replace→反向替換；反向目標比不到→提示「內容已變動，請直接編輯檔案」，狀態不變）。

### users 新欄與常數

- `users.memory_write_mode` String(10) nullable：NULL＝`auto`（預設）／`approval`。走 `schema_upgrade.ensure_schema()` 自動補欄。
- 上限常數集中 `services/memory_files.py` 頂部：`USER_PROFILE_MAX = 800`、`COMPANION_NOTES_MAX = 600`、`SOFT_RATIO = 0.8`（len() 字元計數，與現行 800 字語意一致）。調檔位＝改一處。

## §3 Review pass 寫入管線

### 觸發與素材

觸發點：`run_end_of_chat_pipeline` 第 3 步**整個取代** `process_interaction_note_update`；同一入口供 ingestion（§4）與未來 onboarding 收納呼叫。維持同步執行（現行筆記更新同節奏）；失敗只記錄不擋日記主流程（沿用現行容錯語意）。連線紀律照鐵律：讀→關→LLM→開→寫。

單次 LLM 呼叫的素材：
- 兩檔現況（各附「目前 X／上限 Y 字」；≥80% 時附「空間快滿了，請趁這次合併同主題、刪過時、抽象成 pattern」）
- 近期對話（現行 `format_chat_content`）＋今日日記全文
- 當日 valence 經 `day_stamp.is_negative` 轉語氣提示（低落日→溫柔記錄、不寫成就清單）
- 近 14 天 day_notes（印章＋小語＝兩週情緒軌跡一眼可見）
- （懶遷移時）舊互動筆記，見下
- （B 落地後）未收納的 onboarding 答案原文（source=`onboarding` 的一次性收納）

### 輸出與套用

模型輸出純 JSON（沿用日記 JSON-tail 解析模式；解析失敗＝本輪不寫入、記 log，絕不污染檔案）：

```json
{"ops": [
  {"action": "add", "file": "user_profile", "section": "重要事件時間線", "text": "- [2026-08-23] ……"},
  {"action": "replace", "file": "companion_notes", "target": "舊句原文", "text": "新句"},
  {"action": "remove", "file": "user_profile", "target": "過時句原文"}
]}
```

`{"ops": []}` 合法——平凡的一天可以什麼都不記。

套用引擎（`services/memory_review.py`，純 Python）：
1. 逐筆驗證：file/action 合法、section 在該檔白名單（正規化比對，容忍 `## ` 前綴與空白）、replace/remove 以精確 substring 定位（取第一次出現）。**比不到→該筆 failed 跳過，其餘照套**。add＝插入該章節末行；檔案不存在時以章節骨架模板建檔。
2. 全部套完檢查硬上限：任一檔超標→帶「超標 N 字，請整併」回饋**重試一次**（對原始檔案重新生成整批 ops，棄第一批）→仍超標→**整批拒絕**、檔案不動、帳本記 failed(over_budget)。
3. 自動制：寫檔＋ops 記 applied。核可制：只寫 ops(pending)，檔案不動；核可時逐筆以當下檔案重驗套用。
4. 並發保底：同使用者兩條管線幾乎同時收尾時，後到批次的 target 可能比不到→自然落入 failed，帳本可見（本地單人 app，機率極低，不加鎖）。

### 提示詞與遷移

- 新 `memory_review_prompt.txt`（zh-TW／en 兩語）：策展哲學入文——記 pattern 不記流水帳、只記他實際說過的、不推測不診斷不標籤（v1 鐵律）、日期慣例、寧可不記不亂記。role 沿用 `note_taker`。新增 .txt 檔確認進版控（.gitignore 歷史坑）。
- **懶遷移（零手動步驟）**：review pass 讀素材時，若兩檔皆空且 `interaction_notes` 有最新筆記→附入素材並指示「這是舊版筆記，把仍然重要的內容分流進兩檔」（該批 ops 較多屬正常）。**seed 前**的對話注入 fallback 到舊筆記（現狀不退化）；seed 後新檔接手，舊筆記不再入素材。
- end-of-chat 回應形變：`interaction_note`／`interaction_note_error` 欄位移除，改 `memory_review = {batch_id, applied, pending, failed}` 計數；前端消費點同步更新。

## §4 注入與三邊接縫

### 對話與 check-in 注入

`conversation_prompt.txt` 現行【你對這位使用者的長期認識（互動筆記）】區塊改為兩個 placeholder（兩語同步；`build_conversation_system` 加對應 format key）：

- `{user_profile_block}`——由 `services/user_profile.py: get_user_profile_block(user_id, lang)`（B 的接縫契約函式，C 實作）渲染：【你對這位使用者的長期認識（使用者檔案）】＋檔案內容＋**緊貼區塊的使用說明**（日期時效、自然記得不複誦——鐵律）。fallback 鏈：新檔有內容→新檔；兩檔皆空且有舊互動筆記→舊筆記（懶遷移期）；皆無→「你們還不熟」佔位（永遠非空，模型不見空區塊標題）。
- `{companion_notes_block}`——【你自己的陪伴筆記（寫給自己的，別向他展示）】＋內容＋緊貼說明；空→整塊空字串消失（比照 `companion_block` 模式）。

【如何使用記憶】段措辭同步微調（「筆記」→「檔案」），引用過往日記的規則不動。check-in：`build_checkin_prompt` 的 `user_profile` 參數改餵同一組 block（「進行中的關注」正是 check-in 最需要的素材）；皆空才用現行「還不熟」佔位。記憶檔只在 review pass 後變動，session 內天然穩定。

### Spec B 接縫（雙向成立，不依賴實作順序）

- **C 先落地**（現況既定路徑）：`services/user_profile.py` 由 C 建立；B 之後在同一函式內部加「未收納 onboarding 答案」的【他初次見面時告訴你的】渲染，並於 onboarding complete 時呼叫 C 的 review pass（source=`onboarding`）把答案收進使用者檔案，收納後 raw 區塊自然消失。
- **B 先落地**：C 照 B spec 原契約重寫函式內部。
- 兩個呼叫端、placeholder 名稱、`onboarding_answers` 表、B 的其餘設計全不動。

### Spec D／E 接縫

```python

def run_review_pass(user_id, cfg, lang, *, source, chat_history=None, diary=None, extra=None) -> ReviewResult

```

- `ingest_diary`＝以單篇日記為素材的 review pass（無對話歷史），source=`diary_ingest`。D 只管儲存時溫暖詢問，同意→呼叫本函式。
- E：review pass 收 `LLMConfig`（現行 resolve 鏈）；「背景任務用便宜/本地模型」未來在 resolve 層加選項即可，C 不預作 UI。
- 情緒：素材裡的情緒判定**只**經 `day_stamp.is_negative`＋valence＋day_notes 軌跡——使用者的專用情緒識別模型未來從這一點換入，review pass 呼叫端不動。

## §5 治理與設定頁 UI

（視覺定稿見文件頭 mockup 連結；樣式全取 app 現有 token。）

### 設定 modal 新增「記憶」區

- 模式開關（checkbox，i18n 兩語溫暖文案）：**「記下關於你的事之前，先問過你」**——關＝自動制（預設）／開＝核可制；hint 說明兩制差異與帳本保障。
- 「**管理記憶**」按鈕→獨立記憶管理 modal；核可制且有 pending 時帶琥珀色數字徽章＋「N 件事等你點頭」。

### 記憶管理 modal（獨立 modal，三 tab）

1. **使用者檔案**／2. **陪伴者筆記**：textarea 全文編輯＋即時字數 `x／上限 字`（≥80% 轉琥珀色＋「空間快滿了——下次寫筆記時我會順手整併」）；超標存檔鈕禁用（前端）＋後端 422 雙層防守；「還原」捨棄未存編輯。儲存＝帳本記 `user_edit` 一筆＋指向舊文字的 pending 全標 stale。
3. **記憶帳本**：按 batch 分組（日期＋「來自日記《標題》」／「你自己的編輯」），每筆 op 友善渲染（＋新增／✎改寫／−刪除 圖示色分＋內容＋狀態 chip 六態）。操作：applied→撤銷；pending→逐筆核可/拒絕＋批次「全部核可／全部拒絕」；failed/stale 附原因說明行。核可制頂部有模式提示條（「你開著『記下之前先問我』——你點頭它們才會成為我的記憶」）。

### 溫暖通知（核可制才有）

日記生成完成、回應 `memory_review.pending > 0` 時，聊天區加一則系統樣式訊息：「今天聊的裡面，有幾件我想記下來的事。等你有空的時候，到設定的『記憶』看看就好，不急。」＋「去看看」連結開記憶 modal。**不寫入 `chat_messages`**（重載不重演，比照 B 腳本訊息慣例）。

### API（新 `api/routes/memory.py`，掛現有 auth 依賴）

- `GET /users/me/memory` → 兩檔內容＋上限＋`write_mode`＋`pending_count`
- `PUT /users/me/memory/files/{file_key}` `{content}` → 全文存檔（超標 422；記 user_edit；pending 連動 stale）
- `PUT /users/me/memory/settings` `{write_mode: "auto"|"approval"}`（白名單外 422）
- `GET /users/me/memory/ops?limit&offset` → 帳本新→舊
- `POST /users/me/memory/ops/{id}/approve|reject|undo`；`POST /users/me/memory/batches/{batch_id}/approve|reject`

## §6 FTS5 檢索升級（基礎盤）

- 新虛擬表 `diary_fts`（FTS5）：`seg_title / seg_summary / seg_content / seg_note`（day_note 小語）＋`diary_id / user_id`（UNINDEXED）。**入索引前 jieba 斷詞**（FTS5 內建 tokenizer 不切中文詞；查詢端 `extract_terms` 已用 jieba——查索同一把刀）。
- 查詢：terms OR 串接 MATCH＋`user_id` 過濾，bm25 權重 title 3／summary 2／content 1（對齊現行計分比例）取 top-50 候選，維持現有 Python 重排（bm25 × `_recency_emotion_factor`——情緒因子替換接口不動）、排除今日、TOP_N=3、與語意軌交錯合併**全不動**。
- 同步：日記 create/update/delete 於 crud 層重建該列（Spec D 編輯日記自然覆蓋）；`upsert_day_note` 時把小語併入該日記列重索引。
- 建表：`ensure_schema` 擴充 `CREATE VIRTUAL TABLE IF NOT EXISTS`（冪等）。**降級保險**：FTS5 不可用（罕見自編譯 SQLite）→ 靜默退回現行 LIKE 路徑（`search_diaries_by_terms` 保留），比照 fastembed 慣例。
- backfill：啟動時背景執行緒自動補（表空才跑、不阻塞 startup，比照 embeddings 模式）＋ CLI `python -m services.diary_fts --backfill`。

## §7 測試與驗收

### 後端（pytest）

- ops 引擎全矩陣：add/replace/remove 各檔各章節、target 比不到→failed 不擋其他筆、section 白名單、超標→retry→整批拒絕、空 ops、檔案懶建立含模板。
- 治理：auto/approval 分岔持久化、事後核可 stale 偵測、undo 三種反向 op＋反向比不到分支、user_edit 使 pending 失效、直接編輯超標 422、write_mode 白名單。
- 懶遷移：兩檔空＋舊筆記→素材含舊筆記；seed 前注入 fallback 舊筆記；seed 後不再附。
- 注入：`get_user_profile_block` fallback 鏈三態兩語；companion_notes_block 空消失；check-in 合成三情境；兩語 `conversation_prompt.format()` 花括號 smoke。
- review pass：JSON 解析防壞輸出（壞 JSON→不寫入不炸）、低落日語氣提示分支、day_notes 素材組裝、end-of-chat 回應新欄位。
- FTS：建表冪等、寫入/編輯/刪除同步、user 隔離、bm25 排序 sanity、day_note 併入、FTS 不可用降級 LIKE、backfill。
- API：memory 全端點 auth＋驗證。
- 新提示詞兩語 .format() smoke；`ensure_schema` 補 `memory_write_mode`。

### 前端（vitest）

- 設定區：開關持久化、管理鈕徽章顯隱。
- 記憶 modal：三 tab 載入/切換、字數計數與 80% 琥珀態、超標擋存、還原、帳本六狀態渲染、核可/拒絕/撤銷/批次操作、stale/failed 原因行。
- 溫暖通知：pending>0 才出現、不寫入聊天持久層、「去看看」開 modal。
- i18n 鍵兩語齊備。

### 驗收鐵律（照舊）

使用者本人以 grok 實測：對話→日記→帳本出現合理 ops；隔次對話陪伴者記得新事實；切核可制走完 pending→核可→生效→撤銷一輪；直接編輯檔案後下次對話生效。自動化測試不取代這一條。
