## Spec B 對話體驗——設計

### 中文

```text
我要開始 v2.5 Spec B「對話體驗」的設計，用 superpowers:brainstorming 跑完整
流程（釐清→方案→分節設計→spec 文件→writing-plans）。背景先讀記憶
urdiary-v2-5-ideas 與 urdiary-tone-feedback。

範圍兩件事：
1. 對話人味（#4）：目前像「話少的好哥們」。方向＝情緒鏡映段落（先反映感受
   再回應內容）、few-shot 對話範例、主動追問與記憶引用；以 grok-4.3 為調校
   目標並 A/B 排除模型風格因素。歷史教訓：防禦性規則要配正向許可；persona
   禁詞 grep 鐵律照舊。
2. 初次對話 onboarding（#6）：AI 自我介紹＋一次一題輕量提問（名字、住哪、
   喜歡的食物、重要的人、興趣、擅長、覺得自己是什麼樣的人），全程掛著
   「想直接跟我開始對話也沒關係！」；所有系統訊息發送前隨機「思考」1–3 秒
   （用現成的搖擺思考泡泡；測試中必須可關）。

onboarding 答案的儲存格式要預留給 Spec C 記憶系統（使用者檔案）——設計時把
接口留好，不要先做死。
```

### English

```text
Start the design for v2.5 Spec B "Conversation Experience" using
superpowers:brainstorming, full flow (clarify → approaches → sectioned design →
spec doc → writing-plans). Read memories urdiary-v2-5-ideas and
urdiary-tone-feedback first.

Two items in scope:
1. Conversational warmth (#4): the companion currently feels like a terse buddy.
   Directions: an emotion-mirroring section in the persona prompt (reflect the
   feeling before responding), few-shot dialogue exemplars, proactive follow-ups
   and memory references; tune against grok-4.3 and A/B against other models to
   rule out model style. Lessons on file: defensive prompt rules need positive
   permissions as counterweight; the persona forbidden-words grep rule stays.
2. First-run onboarding (#6): the AI introduces itself, then asks light questions
   one at a time (name, where you live, favorite food, important people, hobbies,
   strengths, how you see yourself), always with an "it's totally fine to just
   start chatting!" escape hatch; every system message is preceded by a random
   1–3 s "thinking" delay (reuse the swaying thinking bubble; must be
   disableable in tests).

The onboarding answers' storage format must leave a clean interface for Spec C's
memory system (user profile) — design the seam, don't hard-code it.
```

## Spec C 記憶系統 2.0——設計

### 中文

```text
我要開始 v2.5 Spec C「記憶系統 2.0」的設計，用 superpowers:brainstorming 跑
完整流程。藍本＝NousResearch Hermes Agent 的記憶設計（要點已存在記憶
urdiary-v2-5-ideas；官方文件
https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/memory.md

陪伴者互動筆記（例：「他累的時候不喜歡被追問」）；日記生成後跑 review pass；
設定頁可檢視/核可 pending 記憶（呼應本專案 consent 哲學）；現有雙軌記憶
升級 FTS5。#8 的「讓模型閱讀我的修改」consent ingestion 接口一起設計。
情緒相關判定沿用可替換接口（backend/app/services/day_stamp.py 的
is_negative——未來換成我的情緒識別模型）。
```

### English

```text
Start the design for v2.5 Spec C "Memory 2.0" using superpowers:brainstorming,
full flow. Blueprint = the NousResearch Hermes Agent memory design (key points
already in memory urdiary-v2-5-ideas; official doc
https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/memory.md
if needed):
- two small always-on files (agent notes + user profile) injected into the
  system prompt every session
- hard character caps that force curation (over-limit writes error and must be
  consolidated in place; patterns, not logs)
- a memory tool with add/replace/remove; a post-conversation background review
  pass (can run on a cheap model)
- a write_approval governance gate (pending / approve / reject)
- full-text history search as a separate layer (SQLite FTS5, zero token cost)

Mapping to URDiary: the user profile ingests Spec B onboarding answers plus
observed long-term patterns; companion interaction notes (e.g. "doesn't like
being pressed when tired"); run the review pass after diary generation; a
settings page to view/approve pending memories (this project's consent
philosophy); upgrade the existing dual-track memory with FTS5. Design the #8
"let the model read my edits" consent-ingestion interface together with this.
Emotion decisions keep the replaceable interface (is_negative in
backend/app/services/day_stamp.py — later swapped for my own emotion-recognition
model).
```

## Spec D 日記本體——設計

### 中文

```text
我要開始 v2.5 Spec D「日記本體」的設計，用 superpowers:brainstorming 跑完整
流程。背景先讀記憶 urdiary-v2-5-ideas。

範圍（#8）：使用者可在日記頁自行創建日記、修改任何日記（AI 生成與手寫不做
視覺區分——都是日記）。每次儲存時，用「要讓我猜猜你今天的心情嗎？」的溫暖
口吻詢問兩件事：要不要跑情緒分析（重算 valence/arousal，會多一次 LLM 呼叫）、
要不要讓模型閱讀這次內容來改善長期記憶（接 Spec C 的 consent ingestion；
C 未完成前先留乾淨的 stub 接口）。

既有約定要遵守：刪日記功能若在本 spec 出現，服務層要同步把該日記的
day_notes.source_diary_id 置 NULL（Spec A 設計文件 §6 的前瞻註記，不依賴
SQLite FK pragma）。
```

### English

```text
Start the design for v2.5 Spec D "Diary Editing" using superpowers:brainstorming,
full flow. Read memory urdiary-v2-5-ideas first.

Scope (#8): users can create diaries themselves on the diary page and edit any
diary (no visual distinction between AI-generated and handwritten — they're all
diaries). On every save, ask two things in the warm voice of "want me to guess
how today felt?": whether to run emotion analysis (recompute valence/arousal —
costs one LLM call), and whether the model may read this content to improve
long-term memory (hooks into Spec C's consent ingestion; leave a clean stub
interface until C lands).

Standing agreement to honor: if diary deletion appears in this spec, the service
layer must set day_notes.source_diary_id to NULL for that diary (forward note in
Spec A design §6; do not rely on the SQLite FK pragma).
```
